## Objective

Drizzle ORM + expo-sqlite wired with the full six-table schema (ARCHITECTURE §4), versioned generated migrations, an idempotent category seed, and a migration-failure gate screen. After this plan, the app boots into a working (empty) relational store.

## Context

The whole app is local-first on SQLite (PRD NFR-1). Decision A1: Drizzle ORM with schema-as-TS. Money is integer sen everywhere (`*_sen`). The financial engine (009) and all repositories build on this schema; testability of SQL without an emulator comes via a Node-side harness (better-sqlite3) reusing the same generated migrations.

## Requirements

- Drizzle + expo-sqlite client initialized once at startup; `PRAGMA foreign_keys = ON` per connection; WAL journaling on.
- Schema (7 tables) exactly as ARCHITECTURE §4: `users`, `categories`, `accounts`, `expenses`, `budgets`, `commitments`, `commitment_payments` — including `money_sen` naming, FK constraints, the unique `expenses.commitment_payment_id` link (D3), `UNIQUE(category_id, month, year)` on budgets, **`user_id` FK on all five financial tables** (user-scoped data, A10) and **UNIQUE email on `users`**.
- Migrations generated by drizzle-kit, committed under `drizzle/`, applied automatically at startup on a versioned bookkeeping table (idempotent, order-preserving).
- Seed: 12 default categories (PRD EXP-7) inserted exactly once (idempotent on empty table). The seeded default **user** (ooiguancheng18@gmail.com / 1234) is created in 003 — it needs the Argon2 hasher, which belongs to the auth feature.
- Every financial repository query is user-scoped (`WHERE user_id = ?`) from plan 004 onward; this plan just carries the indexed columns.
- Migration failure → full-screen error with Retry (PRD NFR; ARCHITECTURE §11).
- Node-side test harness: same schema + migrations run against `better-sqlite3` (dev dependency) so repository/migration tests execute in Jest without an Android device.

## Technical Design

### Files

```
src/db/
├── schema.ts      # drizzle sqlite-core definitions + exported $infer types
├── client.ts      # openDatabaseSync('spending.db'), drizzle(client), pragmas
├── migrate.ts     # runMigrations(): reads drizzle/ SQL, applies, seeds
├── seed.ts        # insertDefaultCategories() — idempotent
└── index.ts       # barrel: client + migrate + types
drizzle.config.ts  # schema path, out=drizzle, dialect=sqlite
drizzle/*.sql      # generated
```

### Schema notes (per ARCHITECTURE §4)

- `users`: id, email (UNIQUE, COLLATE NOCASE), password_hash (Argon2id encoded string), created_at.
- `accounts`, `expenses`, `budgets`, `commitments`, `commitment_payments` carry `user_id` FK (indexed) — every user's data is isolated; `categories` stays **global** (no user_id).
- **Fold later-approved additions into this initial migration set (no reschema churn):**
  - `settings` table (plan 010/016): `(user_id PK/FK, safety_buffer_sen default 30000, ai_active_provider, ai_model_gemini, ai_model_deepseek, updated_at)` — user preferences, **never secrets** (AI keys live in SecureStore, plan 013).
  - `commitments.archived_at` (TIMESTAMP NULL) — C1 soft-delete (plan 008).

- `expenses.date` is TEXT `YYYY-MM-DD` (local calendar; month/year derived in the engine, 009).
- `commitments.total_sen` is NULLABLE — NULL = ongoing recurring (rent/subscription); fixed installments set it.
- `commitment_payments` stores only **paid** records; pending schedule is derived (A3) — the table has no quasi-infinite rows.
- `budgets.category_id` NULL = overall monthly budget; uniqueness `(category_id, month, year)` gives upsert semantics.

### Startup sequence

Root layout (`app/_layout.tsx`) awaits `initDb()` before rendering tabs:

1. Open connection + pragmas.
2. `drizzle` migrator over committed SQL (creates `__drizzle_migrations` bookkeeping).
3. Seed categories if `categories` empty.
4. Any throw → `<DbErrorScreen onRetry={initDb}>` (re-run is safe: migrations are recorded, seed idempotent).

### Node test harness

- Dev deps: `better-sqlite3`, `drizzle-orm` (already), `drizzle-kit`.
- `src/db/testing.ts`: in-memory better-sqlite3 DB + Drizzle instance running the *same* generated migration SQL (read `drizzle/*.sql`, execute in order) — repositories built on the drizzle client are then unit-testable in Jest. Schema import must not require expo-sqlite at module load (keep expo-sqlite import inside `client.ts` only — `schema.ts` imports only `drizzle-orm/sqlite-core`).

## Edge Cases

- **Re-launch after partial migration**: recorded migrations aren't re-applied; seed re-checked.
- **Fresh install vs upgrade**: same code path (migrations table gates).
- **`foreign_keys` pragma must be re-enabled per connection** (some drivers reset on close/reopen).
- **WAL files**: expo-sqlite manages them; no manual VACUUM in MVP.
- **Seed race**: guarded by single init promise (module-level), so double-tap/remount can't double-seed.
- **Date TEXT format**: enforced by engine/forms later; DB layer stores what it's given (validation lives in services, 004+).

## Security Considerations

- DB file lives in app-private storage (OS sandbox); nothing else needed until AI (012).
- No user data leaves the device in this plan.

## Tests

- Migration harness: fresh in-memory DB applies all generated migrations with no error; tables/FKs exist (sqlite_master checks).
- Seed idempotency: run seed twice → exactly 12 categories.
- FK behavior: inserting an expense with a bogus `category_id` throws.
- Constraint checks: budgets unique key rejects duplicates; `commitment_payment_id` unique on expenses.
- CRUD smoke per table (insert/select round-trip with sen integers, no float coercion).

## Acceptance Criteria

1. Fresh app install boots to tabs (no crash) with schema applied; startup with an injected failing migration shows the retry screen, and Retry succeeds.
2. Categories table contains exactly the 12 defaults, once.
3. `npm test`: migration/seed/constraint suite green under better-sqlite3.
4. `drizzle-kit generate` produces no diff against the committed schema (config committed, reproducible).
5. No float anywhere: all money columns resolve to integer-backed column types.

## Out of Scope

- Repositories (003+), seed UI, user-data features, encryption at rest, remote DB.
